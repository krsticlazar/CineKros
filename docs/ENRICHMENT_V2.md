# Offline Catalog Enrichment — B04 v2

Version: `B04-ml32m-tmdb-v2`. Approved source and null policy: Lazar, 2026-09-25. This contract supersedes B04 v1 for future implementation. The previous IMDb-to-TMDB `/find` flow and its worker attempt are historical, not implementation inputs.

## Boundary and inputs

- Preserve every one of the 9,730 accepted `B1a-v1` movies, in ascending `movieLensId` order. B1a remains the authoritative title, year, raw people and IMDb ID source. Tag Genome 2021 remains the only semantic-tag source.
- Use the local MovieLens 32M `links.csv` and `movies.csv` by exact integer equality `B1a.movieLensId == movieId`. Verify source checksums/headers, unique positive IDs and a single row in each table. A matched `links.csv` IMDb ID must equal the B1a IMDb ID after stripping leading zeroes for comparison only. Any duplicate/conflicting row or identity contradiction fails the run rather than selecting a candidate.
- The 9,585 verified exact matches are used directly. The 145 missing from both tables remain in the catalog with null MovieLens 32M-derived fields. Exact IMDb reconciliation found no additional candidate; no secondary/fuzzy/manual mapping is performed in B04 v2.
- From a matched `links.csv` row, accept a positive `tmdbId` or null. Its IMDb value is a cross-check, not a replacement for B1a `imdbId`. From `movies.csv`, parse its pipe-separated `genres` in source order as nonblank unique strings. An absent row or exact `(no genres listed)` sentinel yields null `genres`, not an invented genre. Source-invalid values fail validation; do not silently repair them.
- Stream `ratings.csv` with strict CSV/UTF-8 and invariant decimal parsing. Aggregate only selected matched `movieId`s. `ratingCount` is the number of valid rating rows; `averageRating` is the exact decimal sum divided by count, with no explicit rounding. A matched film with zero rows has `ratingCount=0`, `averageRating=null`. An unmatched film has both fields null because there is no selected 32M identity. Keep rating values out of `semanticText`.

## TMDB details only, offline

- Only matched records with a positive `tmdbId` are eligible for TMDB API v3 `GET https://api.themoviedb.org/3/movie/{tmdbId}`. The runtime CLI reads the bearer credential only from the process environment key `TMDB_READ_ACCESS_TOKEN`; an external launcher may set that key, but this ETL does not parse `.env` or accept a token CLI argument. Fake tests inject the HTTP seam and never need/read a real credential. Do not log the token or authorization header. There is no `/find` request, IMDb-to-TMDB fallback, title/year search or runtime recommendation request to TMDB. The 145 unmatched and eight matched records with blank `tmdbId` make zero TMDB requests and retain null TMDB-derived fields.
- Accept only the requested ID's details (`id` must match the selected `tmdbId`). Normalize nullable positive `runtimeMinutes` from `runtime`, nullable nonblank `originalLanguage` from `original_language`, and nullable relative `posterPath` beginning with `/` from `poster_path`. Missing optional values become null. Reject malformed types/values rather than coercing. Do not retain overview, synopsis, credits, TMDB genres, other TMDB prose, final poster URL or authorization data.
- Cache version `tmdb-cache-v2`; key is the selected positive TMDB ID, not IMDb ID. A valid hashed, versioned, atomic per-ID entry records only `success` or terminal `not_found` and the three approved detail fields. A detail 404 produces `not_found` with all three null; it does not remove the movie or its 32M fields. There is no TTL or automatic refresh; only an explicit set of exact TMDB IDs or a new cache version refreshes. Wrong key/version/shape/hash is invalid and not silently reused. The old `tmdb-cache-v1` entries are incompatible and never migrated implicitly.
- Keep the approved v1 transport policy: 10-second per-attempt timeout; at most three attempts total for network/timeout/429/5xx; honor valid `Retry-After` delta/date, otherwise cancellation-aware 1s then 2s backoff; no retry for other 4xx. A 401/403 configuration failure stops scheduling. Other nonterminal failures create no reusable cache entry and remain resumable; cancellation stops new scheduling and preserves successful cache entries. Concurrency defaults to four and is configurable only in 1–4.
- A real TMDB run needs a separate explicit authorization and request/time cap. B04 v2 implementation verification uses fake HTTP only. Backend/recommendation requests read imported metadata and never contact TMDB.

## Export and provenance

The versioned enriched UTF-8 JSONL preserves the exact eight B1a properties and appends, in this order: `tmdbId` (positive integer or null), `genres` (array of strings or null), `averageRating` (decimal number or null), `ratingCount` (nonnegative integer or null), `runtimeMinutes` (positive integer or null), `originalLanguage` (nonblank string or null), `posterPath` (relative string or null). It never emits per-record cache/failure status or semantic text. For 145 unmatched records, all seven fields are null. For eight matched records with no TMDB ID, 32M genres and rating aggregates remain, while the three TMDB detail fields are null.

The manifest records B1a and 32M input paths/hashes, mapping/cache versions, TMDB API v3, request-policy configuration, cache content hash, output hash/count/order, primary matched/unmatched counts, eight no-ID skips, valid rating rows/target sums, and sorted TMDB success/not-found/nonterminal-failure ID/count classes. The canonical content fingerprint excludes timestamps. Each successful export uses a new, initially absent output directory: build and validate JSONL plus manifest in a same-volume staging directory, then atomically rename that directory to the final output directory. Never overwrite an existing successful output directory. Publish the final pair only after every eligible TMDB ID has a compatible terminal cache entry and all input/output checks pass; interruption or nonterminal failure must leave every previous final directory intact and preserve resumable checkpoint evidence. Never substitute null details for a transient failure and call the export complete.

TMDB attribution remains a global UI/About requirement, not a per-movie field. This stage does not implement hard filters, but its null fields obey the project invariant: an active hard filter does not admit an unknown/null value. It does not define B3, PostgreSQL schema, ranking or evaluation policy.
